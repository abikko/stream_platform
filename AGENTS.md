# Правила работы с проектом

Проект учебный, но пишем его как боевой сервис. Правила ниже — принятые решения. Код, который им ещё не соответствует, приводим к ним постепенно, отдельными правками.

## Режим работы

- Общайся с пользователем на русском языке.
- Go-код и SQL пишет пользователь. AI-агент ревьюит, объясняет и задаёт наводящие вопросы, но готовых решений за пользователя не пишет.
- AI-агент делает коммиты и пушит каждый сразу после коммита, не копя локальные. Также ведёт README. README — краткая шпаргалка по локальному запуску, а не полная документация. Обновляй её при изменении запуска или настройки.
- Перед изменениями изучай существующий код и следуй его соглашениям. Делай минимальные изменения для текущей задачи.
- Не меняй чужие изменения и не выполняй разрушительные Git-команды без запроса.

## Структура

- Слои: `httpapi` (HTTP) → доменный пакет (бизнес-логика, например `identity`) → `postgres` (хранилище). Сборка зависимостей — только в `cmd/main.go`.
- Доменный пакет не импортирует ни `net/http`, ни драйвер БД. Сервисы принимают простые значения (`email, password string`), а не HTTP-типы.
- Интерфейсы объявляет потребитель, в своём пакете. Один маленький интерфейс на сервис, только с нужными ему методами; называем по умению (`UserCreator`, `UserFinder`), не `Base...`.
- У каждого слоя свои типы: в `httpapi` — с тегами `json`, в `postgres` — с тегами `db` (приватная `userRow` + перевод в доменный тип), в домене — без тегов.
- Соглашения (слои, ошибки, контракты, именование) фиксируем в этом файле заранее, до кода, — чтобы не переделывать уже написанное.
- Код (пакеты, типы, интерфейсы) добавляем по мере задач, а не впрок: заготовка под догадку о будущем обычно не сбывается и уводит проект не туда.
- Не добавляй зависимости без необходимости; предпочитай стандартную библиотеку Go.

## Ошибки

- У домена один тип ошибки — `*identity.Error` с полями `Code` (константы `Code...`) и `Fields` (список ошибок по полям, только для `CodeValidation`). Объявляется в одном файле `errors.go` доменного пакета. Наружу, в handler, домен возвращает только его.
- Сентинелы (`ErrXxx`) — заранее созданные экземпляры этого типа для ошибок без данных: `var ErrInvalidCredentials = &Error{Code: CodeInvalidCredentials}`. Сентинел только возвращают и сравнивают, никогда не меняют: нужны данные — создаём новый `&Error{...}`.
- Ошибки валидации — новый `&Error{Code: CodeValidation, Fields: ...}` со списком ошибок по полям — сразу все, а не первую. Ошибка поля — это имя поля и код; текста для человека в домене нет. Параметры (например, лимит длины) добавим, когда они понадобятся в тексте.
- Store переводит ошибки драйвера в доменные сентинелы (`pgx.ErrNoRows` → `ErrUserDoesNotExist`, код `23505` → `ErrEmailAlreadyInUse`).
- Каждый слой добавляет контекст через `fmt.Errorf("...: %w", err)`. Никаких `%v` для ошибок и никаких проглоченных ошибок (`_`, проверка только одного случая).
- Проверка ошибок — через `errors.Is` для сентинелов и `errors.AsType[*identity.Error]` для разбора по коду, не через `==`.
- Логирует ошибку только тот, кто её обрабатывает, — handler. Клиенту на 500 отдаётся общий текст, детали только в лог.
- Смысл ошибки определяет домен (например, логин сам переводит «нет пользователя» в `ErrInvalidCredentials`), а HTTP-слой только выбирает, как о ней сказать. `Code` домена — не код API: совпадение сейчас удобно, но `code` в ответе выбирает `httpapi`.

## HTTP

- Метод указывается в шаблоне маршрута: `mux.HandleFunc("POST /login", ...)`.
- Коды: `400` — некорректный запрос (битый JSON, пустые поля), `401` — неверные учётные данные или токен, `403` — нет прав, `409` — конфликт состояния, `500` — внутренняя ошибка.
- Каждая ветка handler'а явно пишет ответ: если ничего не записать, `net/http` отправит `200`.
- Заголовки выставляются до `WriteHeader`.
- Ошибку `Decode` проверяем сразу. Неизвестные поля в запросе игнорируем (`DisallowUnknownFields` не используем), чтобы клиент мог выходить раньше бэкенда.
- В ответы поля только добавляем; удаление и переименование ломают контракт.
- Ошибки отдаём как `application/json` в одном формате: `{"code": "...", "message": "..."}`. `code` — стабильный машинный код в snake_case, на него опирается клиент; `message` — текст для человека, его можно менять.
- Ошибка валидации: `400`, `"code": "validation_failed"` и список `fields`, где у каждого элемента `field`, `code` (общие для всех полей: `required`, `too_long`, `invalid_format`) и `message`.
- Неизвестная ошибка: `500`, `"code": "internal_error"`, общий текст; детали — только в лог.
- Перевод доменных ошибок в ответ — `switch` в каждом handler'е: в нём видно, какие ответы даёт эндпоинт, и в нём обязателен `default` с `500`. Handler один раз достаёт `*identity.Error` через `errors.AsType` и делает `switch` по `Code`; всё, что не `*identity.Error`, — `500`. Общие в `httpapi` только хелперы записи JSON-ошибки (заголовок → статус → тело) и перевода `*identity.Error` в `ErrorResponse` вместе с `fields`.
- `404` и `405`, которые `ServeMux` отдаёт сам, остаются `text/plain`; это описано в спецификации.
- CORS — middleware снаружи всех остальных: `Access-Control-Allow-Origin: *` для любого origin, preflight (`OPTIONS` с `Access-Control-Request-Method`) получает `204` и дальше не идёт и в лог не пишется. Запросы без CORS-заголовков пропускаются как есть: CORS защищает браузер, а не сервер. Когда появятся cookie (refresh-токен), `*` заменяем списком origin'ов из env — с credentials браузер `*` не принимает.

## Локализация

- `message` в ответах локализует сервер. Языки: `en`, `ru`, `kk`; по умолчанию `en`.
- Язык выбирается по заголовку `Accept-Language` (разбор — свой, без зависимостей: веса `q`, регион `ru-RU` подходит к `ru`, `*`). Нет заголовка или нет подходящего языка — язык по умолчанию.
- В ответе с локализованным текстом: `Content-Language` с выбранным языком и `Vary: Accept-Language`.
- Локализует только HTTP-слой; домен отдаёт коды. `code` не переводится никогда.
- Переводы — файлы данных `en.json`, `ru.json`, `kk.json` в `httpapi`, встроенные через `//go:embed`. Ключ — код ошибки (`invalid_credentials`) или для полей `field.<поле>.<код>`. Эти файлы пишет и поддерживает AI-агент — исключение из правила «код пишет пользователь»; Go-код загрузки пишет пользователь.
- Новый код ошибки добавляется сразу во все три языка.

## Логирование

- Логируем через `log/slog`: короткое сообщение и поля ключ-значение (`slog.Info("request", "method", r.Method, "status", status)`), а не строку, собранную через `Printf`. Ошибка — поле `"err"`. Формат вывода (`TextHandler`/`JSONHandler`) выбирается один раз в `cmd/main.go` через `slog.SetDefault`.
- Существующие `log.Print*` переводим на `slog` постепенно, отдельными правками.
- Не логируем тела запросов и ответов, заголовки целиком (`Authorization`, `Cookie`, `Set-Cookie`) и query-строку — там пароли и токены. Из запроса — только метод и путь (`r.URL.Path`).

## Документация API

- Контракт HTTP API описан в `auth/api/openapi.yaml` (OpenAPI 3.1). Этот файл пишет и поддерживает AI-агент — исключение из правила «код пишет пользователь».
- Спецификация описывает фактическое поведение handler'ов: коды, тела, примеры. При любом изменении HTTP-слоя AI-агент обновляет её в том же коммите; расхождения между кодом и спецификацией сообщает пользователю.
- Проверка — `make docs-lint` (входит в `make check`), просмотр — `make docs`.

## Безопасность

- Не записывай пароли, токены и другие секреты в код, логи или Git. Секреты — только из env, в `.env.example` — заглушки.
- Пароли — bcrypt; проверка через `bcrypt.CompareHashAndPassword`.
- Логин отвечает одинаково и за одинаковое время для «нет такого email» и «неверный пароль».
- JWT пишем сами на стандартной библиотеке: только HS256 (токен с другим `alg`, включая `none`, отклоняется), подписи сравниваем через `hmac.Equal`, payload читаем только после проверки подписи, `exp` обязателен, секрет из env не короче 32 байт, кодирование `base64.RawURLEncoding`. В payload — только `sub`, `iat`, `exp` и стабильные данные без секретов и личной информации.

## База данных

- Передавай `context.Context` в операции ввода-вывода, поддерживай отмену и таймауты.
- В запросах перечисляй колонки явно, без `SELECT *`.
- Схема меняется только миграциями goose. На данных, которые нельзя потерять, — никаких `DROP COLUMN` с пересозданием: новая колонка, перенос данных, потом удаление старой.

## Тесты и проверки

- Добавляй тесты для новой бизнес-логики и исправленных ошибок.
- Тесты табличные, каждый кейс в `t.Run` с понятным именем. Строки в сообщениях — через `%q`.
- Фейк подменяет только хранилище и умеет только то, что умеет настоящий store. Валидацию проверяем через настоящий сервис.
- Каждый кейс должен падать, если сломать то, что он проверяет.
- Перед завершением запускай `make check` (форматирование, golangci-lint по `.golangci.yml`, тесты); сообщай о препятствиях.
- Находки линтера AI-агент разбирает с пользователем: настоящая проблема, ложное срабатывание или несогласие с правилом — и почему. Исключения и настройки правил в `.golangci.yml` добавляются только после согласия пользователя, узко (конкретное правило и файлы) и с комментарием `#` о причине. `//nolint` в коде не используем.
